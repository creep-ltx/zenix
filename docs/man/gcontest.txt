GCONTEST(1)		Zenix manual

NAME
    gcontest - test a console handed to a display server

SYNOPSIS
    gcontest ack|late|noack [SECONDS [ACCEL | m SET]]
    gcontest keys CODE...
    gcontest mouse DX,DY,BUTTONS...
    gcontest dirty

DESCRIPTION
    A test program for DESIGN D38 step 2 (SYS_console CON_GRAB and
    CON_GACK), run as root by tools/gcon-test.sh. It does what the display
    server does with the console it is started on (its descriptor 0): it
    hands the kernel a Copper list of its own (one blank bitplane: the
    whole screen green; with no bitplane at all FS-UAE shows no sprite)
    and a pointer (sprite 0, a 16 x 16 red square, its hot spot at the
    top left), then writes every record of the ring as a line:

        gcontest: grabbed fd N WIDTHxHEIGHT depth D chips C
        gcontest: key 0xCODE qual 0xQUAL ch B0 B1
        gcontest: pointer X Y qual 0xQUAL
        gcontest: release N        (and with ack: gcontest: ack N -> 0)
        gcontest: acquire
        gcontest: lost N

    ack answers every request to let go (CON_GACK); late answers 2 s later
    (after the kernel's 1 s deadline, the switch has happened; the answer
    still counts: the kernel uses the blitter again); noack never does, so
    the kernel switches after its 1 s deadline, says so in the log and
    draws with the CPU until the program ends. Right after the grab it
    tries to free the grab's memory ("gcontest: memfree ... -> -16":
    refused while the grab lasts). With ACCEL (hexadecimal, THRESHOLD |
    MULTIPLIER << 8) it then sets the mouse's acceleration (CON_MOUSE),
    after trying a wrong one: "gcontest: accel 0x900 -> -22", then
    "gcontest: accel 0xACCEL -> 0". With m SET it sets the whole setting
    of DESIGN D61 instead (CON_MOUSE's struct umouse; SET is
    W,H,GAINX,GAINY,THRESH,MULT,SHIFT,X,Y, numbers as C writes them, the
    ones left out D38's: 640, 256, 0x200, 0x100, 0, 0x100, 0, -1, -1),
    after a wrong one (a gain of 0): "gcontest: set gain 0 -> -22", then
    "gcontest: set SET -> 0"; the pointer's records are then in those
    units. It ends after SECONDS (default 60) or at the q key, giving the
    console back.

    keys types the raw key codes (hexadecimal; bit 7 set for a key going
    up) through CON_INPUT on descriptor 0, as the keyboard would: 66 51 d1
    e6 is Amiga+F2.

    mouse moves the mouse by DX, DY counts (-128..127; a count is two
    hires pixels across, a line down, before the grab's setting) and
    sets its buttons (bit 0 left, 1 right, 2 middle; held until the next
    record) through CON_INPUT's CONI_MOUSE, a record every 3 ticks. The
    desktop's tests drive it.

    dirty fills every piece of free chip RAM it can get (up to 16 pieces,
    512 KB down to 4 KB) with 0xFF and frees it again ("gcontest: dirty N
    KB"). A real Amiga's chip RAM holds old pictures, FS-UAE's starts at
    zero: after this, chip RAM a program forgets to clear shows on the
    screen in the emulator too (tools/drag-test.sh).

NOTES
    With full memory protection (DESIGN D60 6.3) only the display
    service's process may grab a console: gcontest run from a shell is
    refused (-1, EPERM; "is not the display service" in the kernel
    log, once), as tools/mmu-test.sh checks. tools/gcon-test.sh runs
    on the 68020 machine, without an MMU, where root may still grab.
    Root only. A second gcontest while one has the console is refused
    (EBUSY). Its output is meant for a file: the console it writes to is in
    graphics mode while it runs.
