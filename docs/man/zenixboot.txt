ZENIXBOOT(8)			Zenix manual

NAME
    zenixboot - start Zenix from AmigaOS, from files on a disk partition

SYNOPSIS
    zenixboot [KERNEL] [RAM=FILE] [CHECK] [PREVIOUS] [UNSIGNED_OK]

DESCRIPTION
    zenixboot is an AmigaOS program, not a Zenix one. It boots Zenix on an
    Amiga that starts from a hard disk, a CF card or (under Emu68) an SD
    card, so that no Zenix floppy is needed. It is meant to be the only
    line of S:Startup-Sequence on a small AmigaDOS (FFS) boot partition
    that holds nothing but S/Startup-Sequence, zenixboot and the kernel:
    Kickstart boots that partition with its own ROM filesystem and shell,
    and no other AmigaOS file is needed. It also runs from a normal
    AmigaOS shell.

    It does what the floppy's boot block does, with the same code for the
    hand-over (boot/handoff.S): it reads the kernel file (the same image as
    on the floppy, build/kernel.bin, called "zenix" on the boot partition)
    and the optional RAM-disk image, collects the CPU type, the memory list
    and the Pi's hardware addresses (stage0, under Emu68), keeps the top
    16.5 KB of chip RAM free for the kernel log (below exec's MaxLocMem
    rounded down to 4 KB, as the kernel counts), switches AmigaOS off and
    jumps to the kernel. Zenix then finds its root filesystem by itself:
    the RAM disk if one was given, else the first ext2 or ZenixFS
    partition (docs/architecture.md section 9).

    Everything is read and checked while AmigaOS still runs. Any problem
    is printed and zenixboot returns to AmigaOS with nothing switched off;
    from a Startup-Sequence that leaves the boot shell's prompt on the
    screen. Only when the last check has passed does it switch AmigaOS
    off; from then on there is no way back but a reset.

    While it loads, the whole screen is blue; then cyan while the tables
    are collected, magenta when AmigaOS is off: the boot colours of the
    floppy (docs/pi-first-boot.md). On an error the AmigaOS screen comes
    back with the message. Every message is also sent to the serial port
    (9600 baud, through exec's RawPutChar), so a boot can be followed with
    a cable.

    Besides what the boot block switches off (interrupts, DMA, the CIA
    interrupts), zenixboot also stops every floppy motor, shows no screen
    (LoadView of none, so the display registers a Workbench screen set do
    not stay), puts the AGA fetch mode and the bitplane registers back to
    their reset values, waits for the blitter, switches a 68040/68060's
    data cache off (as after a reset) and its MMU off (SetPatch's CPU
    library switches it on; Zenix runs without one).

UPDATES
    With a directory Zenix/ next to zenixboot holding the kernel
    (Zenix/zenix; the boot partition of a card made for updates), the
    kernel is taken from there and zenixboot installs updates (DESIGN
    D15, zup(8)). Without one it takes "zenix" next to itself, as before,
    and does nothing about updates. An update is a bundle in
    Zenix/zenix-update.zup with its signature in zenix-update.zup.sig.
    Zenix's zpkg -Syu writes both there itself (zpkg(8), SYSTEM UPDATES:
    new files in AmigaOS's safe order, nothing else on the partition
    changed), so no AmigaOS step is needed. Copied by hand from AmigaOS
    instead, a file goes as NAME.part first, then renamed: a .part is a
    copy that was cut off and is renamed .bad.

    A new bundle is read whole into memory (fast RAM first) and checked in
    this order: every count, size and offset and the SHA-256 of its table
    (computed over the header's first 64 bytes and the table, and compared
    with the header); whether its kernel can serve this root and the
    volume has room (else it waits, unchecked, for a later start); then
    its signature; then the SHA-256 of every part. A bad one is renamed
    zenix-update.bad with the reason, and the installed system starts; one
    older than the installed version too.

SIGNATURES
    Every bundle must come with its signature, Zenix/zenix-update.zup.sig
    (80 bytes, made by tools/zsign.py on the PC; DESIGN D21 6.1-6.4):
    Ed25519 over the label "Zenix bundle signature v1" and the digest
    zenixboot computed itself, never one read from a file. Copy the .sig
    first (as zenix-update.zup.sig.part, renamed), then the bundle. A
    bundle without one, with one that does not verify, signed by a key
    zenixboot does not know, or of the other kind of channel is renamed
    zenix-update.bad (its .sig zenix-update.bad.sig) with the reason;
    the installed system starts. On success it says which key signed
    and how long the check took ("signed by release key 1a2b3c4d5e6f7081
    (checked in 7.84 s)"). The .sig follows the bundle: renamed .done.sig,
    .rejected.sig or .bad.sig with it; a cut-off zenix-update.zup.sig.part
    is deleted, and a zenix-update.zup.sig with no bundle (left by a cut
    between two renames) is renamed zenix-update.bad.sig.

    Which keys: a release build (make RELEASE=1) knows only the release
    keys (tools/keys/zenix-release-*.pub, built in) and takes only
    bundles of the channels stable and testing; a test build knows only
    its tree's TEST key (made in build/sign-test, never in the
    repository) and takes only the channel test. zenixboot is never
    updated by a bundle, so its keys change only when a new zenixboot is
    copied by hand.

    The check runs once per bundle: the verified digest is written into
    the state file (sigdigest), and the later starts of the same trial
    compare the computed digest with it instead of checking again. The
    check (an estimate of 6-9 s on a 14 MHz 68020) runs on a stack of its
    own (6 KB, StackSwap): its deepest chain is 2,412 bytes, measured with
    gcc's -fcallgraph-info, more than the boot shell's default stack can
    be trusted to leave free. That stack is filled with a pattern first;
    zenixboot says how much of it the check used, and refuses the bundle
    if the check reached its lowest 512 bytes.
    So is one whose kernel cannot serve the machine's root: when the
    installed kernel says it serves ZenixFS roots (the test-only
    kernel-zfs; the shipped kernel has no ZenixFS server, DESIGN D19) and
    the bundle's kernel says it does not. Each kernel says so in its
    version record (ZVER, then ZSRV and the list); an older record says
    nothing, and nothing is refused for it.
    Before any write Info() must say the volume is validated and has room
    for one more kernel, else the update waits for a later start. Then,
    in this order, each step flushed (ACTION_FLUSH to the volume's
    handler, which replies when FFS has written its buffers): the state
    file (installing), zenix.new written, read back and checked, the old
    zenix.old deleted, zenix renamed zenix.old, zenix.new renamed zenix,
    the state file (trial). A cut anywhere is repaired by the next start:
    a zenix that is the bundle's kernel already is not written again,
    zenix.old is never touched twice for one version and never deleted
    while zenix is missing. Every rename deletes its target first (an
    AmigaDOS Rename fails when the target exists).

    The bundle then goes to the new kernel in memory for its root half
    (bootinfo +0x78), at every start of the trial; zup installs it once.
    The trial ends when the update note in the kernel log's area (top of
    chip RAM) says the new version came up (login's prompt on console 1):
    the bundle is renamed zenix-update.done. When the note says it came
    up but its root half failed (zup refused the bundle, or /sbin/zup is
    missing or did not end well), the bundle is kept and goes to Zenix
    again at the next start ("Zenix V came up, but its root half was not
    installed"), and the count of starts begins again. It also ends after
    3 starts with no sign of trouble. A bundle offered again after that
    is renamed .done at once; the previous kernel stays zenix.old.

    Only evidence counts. When a warm reset follows a trial boot whose log
    ended with a panic, or that was still running and never confirmed
    (a hang the owner reset), zenixboot asks "Zenix V crashed - start the
    previous version? (Y in 10 s)"; Y, Return or no key in 10 seconds
    starts the previous version, N the new one. A cold start (switched
    off: chip RAM is gone) proves nothing and never goes back; it says
    "Zenix V was installed and not yet confirmed; if it misbehaves, choose
    Zenix (previous)".

    Going back (PREVIOUS, or Y to the question): the bundle is renamed
    zenix-update.rejected first (a cut never applies it again), zenix
    becomes zenix.rejected and zenix.old becomes zenix, flushed between,
    and the kernel is told "previous" (a flag in bootinfo): zup puts the
    root's previous version back too. With no zenix.old zenixboot says so
    and starts the installed kernel. After that there is no previous
    version until the next update.

    The start rule: Zenix/zenix; if it is missing or not a kernel, a
    zenix.new with the state's SHA-256, then zenix.old; the one used is
    named on the screen and the serial port. The state file Zenix/state
    (text: version, the kernel's SHA-256, the verified signature's digest,
    the phase - installing, trial, confirmed, rejected -, handovers, the
    last boot number; unknown keys are ignored) is written as
    state.new and renamed; a start that finds only state.new uses it.
    zenixboot and bootmenu are never updated by a bundle. CHECK writes
    nothing; RAM= ignores a waiting bundle (its root half needs the disk's
    root).

ARGUMENTS
    KERNEL      the kernel image to start; default Zenix/zenix (the start
                rule above), else "zenix" in the directory zenixboot
                itself is in (PROGDIR:). With KERNEL nothing about updates
                is done
    RAM=FILE    also load FILE as the RAM disk (an ext2 image such as
                build/root-ram.img); Zenix then uses it as its root
    CHECK       do everything up to switching AmigaOS off (load, check,
                collect the tables, choose where the kernel will run),
                say so, and return to AmigaOS; nothing is written, and
                the CM4's Ethernet is left running for AmigaOS (a real
                start stops it first: NOTES)
    PREVIOUS    go back to the previous version (UPDATES above): the
                boot menu's "Zenix (previous)" line
    UNSIGNED_OK a test build takes a bundle without a .sig (it says so;
                a .sig that is there must still verify). A release build
                says it ignores it and refuses unsigned bundles

EXAMPLES
    SYS:zenixboot
        The whole S:Startup-Sequence of the boot partition.
    zenixboot DH1:zenix/kernel.bin RAM=DH1:zenix/root-ram.img
        From a shell: another kernel, with a RAM disk as the root.
    zenixboot CHECK
        Try it without leaving AmigaOS.

EXIT STATUS
    0 after CHECK (or when started from Workbench, which it does not
    support: it returns at once), 20 on any error. On success it does
    not return.

NOTES
    On a PiStorm with a CM4, AmigaOS's network driver may leave the
    Ethernet chip (GENET) writing received frames into memory Zenix is
    about to own. Just before AmigaOS is switched off, the start stops
    the chip's DMA, masks its interrupts and turns its MAC off (the
    kernel's stage0, also on the bootblock path); the boot log says
    "pi: genet: ..." when it found the DMA running. CHECK does not.

    Needs Kickstart 2.04 or newer and a 68020, 68030, 68040 or 68060 (or
    Emu68): on a 68000 or 68010 or under Kickstart 1.3 it says so and
    returns before doing anything. Kickstart 1.3 is not a target.

    Started from a running Workbench, it switches off whatever runs there:
    files being written may be lost and volumes may need validating. Best
    started from a boot partition, or from a freshly booted system. A
    network or USB driver that keeps receiving into memory by DMA (on
    the Pi's side, under Emu68) is not stopped by switching AmigaOS off;
    start zenixboot from a system without them.

    The kernel goes to the start of the largest fast-RAM region (256 KB
    aligned), or to chip RAM at 0x40000 when there is no fast RAM; the
    load buffers are kept clear of that place, of low memory and of the
    kernel log's area, and zenixboot refuses (not enough memory) when
    they cannot be.

    The boot partition is made by tools/mkffs.py and tools/mkcard.py
    (make build/zenix-card.img for an Emu68 SD card, build/zenix-boot.hdf
    for an IDE or CF disk); tools/write-card.sh writes the SD card.

    zenixboot itself is never updated by a bundle (it would have no
    copy in place between two renames): a new zenixboot is copied by
    hand. The updates do not need one: zpkg writes the files this one
    reads.

    Verified in FS-UAE (tools/zenixboot-test.sh; updates and signatures:
    tools/update-test.sh; an update zpkg wrote, installed by the
    zenixboot of the owner's card: tools/sysupdate-test.sh); not yet
    run on a real Amiga. Not verified:
    whether an RTG card gives the monitor back to the chipset when no
    screen is shown.
