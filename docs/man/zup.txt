ZUP(8)			Zenix manual

NAME
    zup - install the root half of a Zenix update

SYNOPSIS
    zup
    zup -l
    zup -f FILE [-d]
    zup -r NAME [-n]

DESCRIPTION
    zup installs the programs and files of an update onto the root
    filesystem. An update arrives as a bundle on the boot partition
    (zpkg -Syu writes it there, zpkg(8)); zenixboot(8) installs its
    kernel, and the new kernel hands the bundle to zup in memory. zup
    needs a kernel that knows updates (SYS_update, Zenix 0.2 of
    2026-10-26 and later); on an older one it does nothing. Only root
    runs it. It does, in this order:

    1. A journal left by a power cut (/var/lib/zpkg/journal): the install
       it describes is finished, if every new file is there, complete and
       checked, or else rolled back. Never anything in between.
    2. A way back: when "Zenix (previous)" was chosen in the boot menu,
       or the running kernel is older than the installed base packages,
       the files of the previous version are put back from
       /var/cache/zpkg/prev-VERSION, and that set is removed: there is
       no "previous" again until the next update.
    3. A bundle: everything is checked before anything changes - the
       SHA-256 of the bundle's table and of every part, that it is not
       older than what is installed, that its base packages are not newer
       than the running kernel (the kernel always goes first), the
       dependencies, and the free space for what it will write; every
       path is absolute, without . or .. parts (also at its end), and
       every package name (also a dependency's) is only a-z, 0-9 and
       + . - (it becomes a file name in /var/lib/zpkg). A refused bundle
       changes nothing. Packages whose version is
       installed already are skipped;
       if all are, zup says so and does nothing. A newer zup is installed
       first, on its own, and then runs for the rest.

    An install is one transaction: the journal is written and synced
    first, the root is marked "needs a check" (ext2), every file that is
    replaced or removed is kept by a hard link in the prev set (no copy),
    each new file is written as PATH.zup-new, read back and checked
    against its SHA-256, its owner set and then its mode, and renamed
    over PATH (a running program keeps running), then the undo record
    and the commit are written, older prev sets are removed and the root
    is marked clean again. A power cut leaves it marked "needs a check".
    The result line (/var/lib/zpkg/result) is written under that mark
    too. ext2 has no journal of its own: a cut inside one block-writing
    step can leave a leak (a link count one too high, blocks or an inode
    nothing names), never a lost or shared block; zup does not repair
    leaks: boot checks the marked root with fsck.ext2 at the next start,
    before zup finishes or rolls back the install (DESIGN D17).

    Config files (marked in a package's manifest: /etc/passwd, group,
    fstab, svctab, motd) are compared three ways: one the owner never
    changed is replaced; one the owner changed stays, and when the
    update brings a different version it is written next to it as
    PATH.new ("kept your /etc/passwd (the new one: /etc/passwd.new)"):
    nothing to do unless you want what is new in it (compare the two
    with diff, copy over the lines you want, then delete the .new; your
    users and passwords are in your own file and stay). When the update
    brings the same version as before, nothing is written or said. One
    the owner deleted is not brought back.

    One package at a time (zpkg(8) runs these; DESIGN D22): zup -f
    installs one package file (a bundle holding one package and no
    kernel) and zup -r removes one package, each as one transaction of
    its own, with the same journal, checks and power-cut safety. They are
    "live": the files they replace are kept in /var/cache/zpkg/live/
    only until the commit, and they never touch a prev set, so the
    system's way back ("Zenix (previous)") stays whole. zup refuses, and
    changes nothing, when: a package of the group base (zup, zpkg, base)
    is named - those change only with the system, at a restart; the
    package is part of the previous system the boot menu can go back to
    (until the next system update); a path belongs to another package
    (directories may be shared; "takes OTHER" in the manifest hands
    OTHER's files over in the same transaction), exists and belongs to no
    package, lies under /var/lib/zpkg or /var/cache/zpkg, or has a
    symbolic link on its way; the version is older than the installed
    one (unless -d) or needs a newer base or another package first; the
    file is a system bundle (those go through zenixboot); a new system
    is on trial (not confirmed yet); another zup, zpkg or zpkg-new is
    changing packages (/var/lib/zpkg/lock); a manifest lists a path
    twice, a name ending in .zup-new, .new or .save (zup's own), a
    link target of other characters than A-Z a-z 0-9 . _ + / -, or more
    than 2,048 entries; a path is on another mount; a downgrade would leave an
    installed package without the version it needs. A system update's
    unfinished journal is left to the next start ("restart first").
    Removing refuses a package another installed package needs. A config
    file the owner changed is kept as PATH.save when its package is
    removed (-n deletes it too; an older PATH.save is never replaced: the
    removal is refused until it is moved away). Directories a removed
    package listed are removed when empty and no other package lists them.
    Ctrl-C, hangups and kill's TERM are ignored while zup works. The file
    is read twice, never held in memory: its SHA-256 first, then unpacked.

    boot(8) runs zup at every start, after the root is mounted and before
    anything else. The result is one line in /var/lib/zpkg/result, which
    login(1) shows after the next login (then it is removed), and a note
    for zenixboot in the kernel log's area (done or failed).

OPTIONS
    -l      list the installed packages and their versions, and whether
            a previous version is kept
    -f FILE install the one package in FILE (zpkg checks its signature
            first; zup checks every SHA-256 again)
    -d      with -f: an older version too (zpkg --back)
    -r NAME remove the package NAME
    -n      with -r: a changed config file is deleted, not kept as .save

FILES
    /sbin/zup                   the program (package zup)
    /var/lib/zpkg/NAME.manifest the installed packages (plain text)
    /var/lib/zpkg/journal       an install in progress
    /var/lib/zpkg/result        the last result, until it was seen
    /var/cache/zpkg/prev-V/     the files the install of V replaced
    /var/cache/zpkg/live/       the files -f or -r replaced, until the commit
    /var/lib/zpkg/lock          the pid of the zup or zpkg that changes
                                packages (a dead one's is stale)

EXIT STATUS
    0 when there was nothing to do or everything worked, 1 when a bundle
    or a package was refused or an install was rolled back, 2 for a wrong
    argument.

NOTES
    zup ignores SIGPIPE: zup | less, and quitting less early, never ends
    an install half-way (its messages just go nowhere then).
    zup sets its own umask (022) first, whatever the caller's (sudo keeps
    it): no file or folder of an install, half-way or kept, is writable
    by others.
    The bundle lies in memory that is no process's own: zup copies what it
    writes through its own buffers (a system call would refuse a pointer
    into the bundle). Only the root filesystem is changed; /home and other
    mounts are not touched. Signatures are not checked yet: whoever can
    write the boot partition can replace the kernel anyway, and the
    checksums catch damage, not a deliberate fake. The formats (bundle,
    manifest, journal) are described in docs/architecture.md section 3,
    "Updates". Verified on the PC (tools/zup-host-test.sh: refusals, the
    three-way compare, a power cut before each change, the way back; and on
    the real ext2 server, a power cut after each block write; the same
    for -f, -r and a takes hand-over, with the prev set checked byte for
    byte). A zup -f or -r cut by a power cut is finished or rolled back
    by zup at the next start (its messages say which; it leaves no result
    line and no note: zpkg can simply run again).
    A test build (UDIAG=-DDIAG_SLOWZUP) hangs when it runs as the second
    stage, for boot's time-limit test (tools/update-test.sh slowzup).
    Every message is on the console the moment zup says it (one write
    each, nothing kept back), so a zup that boot stops after its time
    limit, or a power cut, has shown its last line. The messages are not
    in the kernel log (dmesg): they are zup's output on console 1.
