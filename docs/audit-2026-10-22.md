# Zenix audit, 2026-10-22

Status of each item: when a fix is committed, add "**fixed** (commit)" to its row or line. This is the work list for
the hardening round (see CLAUDE.md "Current focus").

Branch `main` at 4536510, plus a look at `drivers`, `zenixfs` and the uncommitted `floppy` worktree. Five reviewers
read the code (kernel core, drivers and boot, filesystems, userland, build/tests/docs). They also built a
private copy and ran one headless emulator test. Nothing in the Zenix trees was changed.

How each finding is known:
- **confirmed**: traced line by line in the code, or seen in the compiled binary;
- **checked**: confirmed by the reviewer, and then also checked a second time by me;
- **suspected**: the logic points that way, but only real hardware can settle it.

Nothing here has been run on a real Amiga.

## Part 1 - In plain words

**The big picture is good.** The design is sound and fits the Amiga: a small kernel, servers behind message ports,
`spawn` instead of `fork`, ext2 for Linux exchange, and ZenixFS with a careful commit order. The amount built in one
day is large: about 27,000 lines, 84 programs, and a shell that is checked against bash. ZenixFS's crash-safety
design checked out well, and so did the printf formatter and the byte-order handling.

**The weakness is the speed it was built at, with only an emulator to test on.** The emulator hides three kinds of
problem, and all three are present:

1. **Things only real CPUs do.** Code is cached and never refreshed after a program is loaded. A real 68060 lacks
   one multiply instruction that the compiler uses everywhere. One cache instruction throws away unsaved data on
   Emu68. On your PiStorm any of these can give a dead or randomly crashing machine on the first boot.
2. **Things only real timing shows.** The keyboard handshake is an empty counting loop. On Emu68 it is about ten
   times too short, so keys get lost or doubled. Interrupt handlers do heavy work, such as drawing the screen and
   changing workspaces, at the same moment as programs, which the emulator rarely makes collide.
3. **Things only long, real use shows.** Memory is not handed back properly: a failed allocation looks like a
   success, and `free` can give away memory that is still in use. Deep directories overflow program stacks. Deleting
   a short symbolic link frees random disk blocks. A shell left running for a long time runs out of memory.

**For you as the user, the most important practical points:**
- **The Swedish keymap is a PC layout, not the Amiga one.** `|`, `$`, `@`, `{ }`, `[ ]` and `~` cannot be typed on
  your keyboard. In a Unix shell that means no pipes and no variables. Keys also do not repeat when held down.
- **Do not let Zenix near a disk with AmigaOS partitions on it yet.** Its `fdisk` rewrites the partition table with
  its own geometry and can shift every AmigaOS partition. The ext2 server will also mount, and write to, a modern
  Linux ext4 partition as if it were ext2, which damages it. Your PiStorm's SD card holds Emu68 and the Kickstart:
  only boot from the RAM-disk floppy until these are fixed.
- **The RAM-disk floppy image (`zenix-ram.adf`) is broken at the moment.** It no longer fits, and a second `make`
  quietly produces a bad image.
- **Security is weaker than the docs say, even counting the honest no-MMU limit.**
  - Any user can kill the filesystem server.
  - Amiga+Return opens a root shell at the login prompt.
  - Root has no password and is logged in automatically.
  - Any program can read or write any file by sending messages straight to the filesystem server.
- **The docs have drifted.** The same facts get different numbers and statuses in different files: 20, 77 and 84
  commands; "ZenixFS not built" next to "ZenixFS verified"; "tested on a real A1200". (**fixed**, Part 3 item 11.)

**My recommendation:** before more features, spend one round on the **first-boot blockers** (Part 2, batch A) and
the **memory foundations** (batch B). Both are small changes with large effects, and the first weekend on real
hardware will be far more productive with them done. Part 4 is a checklist for that first boot.

### Batch D - permissions, as the docs promise them
- Any user can `kill` any process, including fsd and diskd (syscall.c:457). `setfg` and `ttymirror` take any pid.
  `settime` has no uid check. **fixed** (20393ae): one `may_signal` rule for kill, jobctl and setfg (root; same real or
  effective uid; own child; never the built-in servers or a privileged process); settime and ttymirror root only.
  Verified: users-test (badptr ipc, `kill 1`, kill of root's `sleep`, `date -s` as a user).
- Any user can send `FS_READ`/`FS_WRITE` by inode number, or `FS_QUIT`, straight to the "fs" port, and so bypass
  fsperm.h. diskd checks no uid. After killing fsd, a user can register a fake "fs" port and serve fake setuid
  binaries. Fix: mark kernel-made messages, reserve the names "fs" and "disk", and check `m->uid` in diskd. **fixed**
  (20393ae): `umsg.kflags` (`UMSG_KERNEL` only from `ipc_kcall`, cleared on every `SYS_call`); fsd and zenixfsd serve
  only kernel or root messages; diskd only root (list/info for anyone); `fs`, `fs.*`, `disk` root-only names;
  `proc_spawn` takes set-user-id only from the mount table's server (read: it already did; the name is now root's).
  Verified: badptr ipc on the ext2 and the ZenixFS root, ext2-host-test, disk-host-test.
- Amiga+Return gives a root shell with no login (boot.c:36, syscall.c:154). Root, user and guest have empty
  passwords and autologin is `root`: this must be stated in README/limits.md before any release. **fixed** (20393ae,
  126bf59): no shell while nobody is logged in (session flag in the kernel, ended by init; boot.c untouched); the
  defaults are kept and stated in README, limits.md and login(1); login warns at autologin while root has no
  password. Verified: users-test (the workspace message at the login prompt, the warning line).
- `su` keeps the caller's PATH/HOME and runs their `~/.shrc` as root. Passwords are 100 rounds of SHA-256 in a
  world-readable `/etc/passwd`. A non-numeric uid parses as 0, which is root. `passwd` silently deletes users beyond
  the first 4 KB of `/etc/passwd`. **fixed** (126bf59): su sets the target's HOME/USER/SHELL/PATH=/bin, drops IFS;
  sh skips a ~/.shrc not owned by the effective user or root (verified: users-test); non-numeric ids ignore the line,
  passwd and pw.c read the whole file up to 64 KB (read, not tested in FS-UAE); new hashes `1000$salt$hex`, old ones
  valid (read; 1000 is a choice, not measured on hardware). Still world-readable (no shadow file: a feature).
- `tar x` accepts absolute and `..` paths. `find -delete` follows symlinks out of the tree. Here-document temp names
  are predictable and there is no `O_EXCL` at all. **fixed** (20393ae, 126bf59): tar x strips `/`, refuses `..` and
  names through a link from the same archive; find walks with lstat; `O_EXCL` in the kernel path and both servers,
  used with random names and mode 0600 by sh and mktemp. Verified: users-test on both roots, ext2-host-test.
- setgid directories are not honoured, and a write does not clear setuid. **fixed** (20393ae), with the rest of the
  filesystem review's M10: setgid directories, non-owner write/truncate clears set-user-id, utimes with a given time
  only owner/root, non-root chmod cannot set set-group-id for another group, ZenixFS directory move to another parent
  needs w on it. Verified: ext2-host-test (all), users-test/zroot-test (setgid directory, set-user-id clearing, chmod,
  directory move); utimes on ZenixFS is read only.
- Found on the way, not fixed: `mv` falls back to copy + remove on any rename error (so a refused rename can still
  move by copying what the user may read and delete); the ext2 server's `O_CREAT` without `O_EXCL` on a dangling
  symbolic link may add a second entry of that name (read, not checked). **fixed** (0d501f5, 43d6113): mv copies only on
  -EXDEV (verified: users-test mv-dir, batch-e mv of a directory on ext2); the dangling link case was real (read:
  `ext2_namei` failed, `ext2_create` added the name) and now answers -ENOENT in both servers (read; O_EXCL's case is
  verified by badptr ipc).

### Batch E - correctness that will bite in daily use
- `tty_of()` falls back to tty 1. `ls | less` on workspace 2 reads keys from, and puts into raw mode, workspace 1
  (tty.c:44). Store a controlling tty in `struct proc`. **fixed** (b2efff5): `ctty`, the console of fd 0 at spawn, else
  the parent's. Verified: users-test "less-st=0" (`ls /bin | less` on console 2, q typed there).
- Shell:
  - arena leaks per loop iteration, so long `while read` scripts die with "out of memory";
  - history recall copies a 2 KB entry into a 480-byte line;
  - the tab-completion buffer overflows;

## Part 3 - Vision, roadmap and design observations (my own view)

1. **Target versus the machine you actually have.** Principle 6 says "real A1200 with an IDE board first". Your
   machine is a PiStorm: Emu68 is effectively a very fast 68040 JIT with its own cache rules, and every critical
   item in batch A is worse there. I suggest naming two first-class targets in the ROADMAP: "stock A1200 + IDE" and
   "PiStorm/Emu68". Write down the Emu68 rules (cache flushes, timing that does not depend on the CPU) as
   project-wide coding rules in CLAUDE.md, so new code does not reintroduce them. The new knowledge note
   `amiga/emu68-jit-cache-rules.md` is the source.

2. **The data cache can be on without an MMU.** start.S keeps the data cache off "because there is no MMU to mark
   chip RAM uncached". On 68030 and up that is not true:
   - the 030 has TT0/TT1, the 040/060 have ITT0/1 and DTT0/1, and the EC parts have ACR0/1;
   - these transparent-translation registers set cache mode by address range with paging off, so chip RAM
     (0-0x1FFFFF) can be cache-inhibited while fast RAM is cached (copyback on 040/060).

   An 040/060 with the data cache off loses a large part of its speed, so this matters for "AmigaOS speed"
   (Principle 9). It needs the matching cache pushes for DMA buffers (SD mailbox, A3000 bounce buffer). This is
   *proposed*; it needs measuring on hardware. Under Emu68 the effect may be small.

3. **"One way to do a thing" is slipping in small places:**
   - two path normalisers;
   - six path-join copies;
   - two glob matchers;
   - nine copies of "read a directory into an array";
   - two ways to find programs (`$PATH` versus a fixed `/bin/` in find, xargs and timeout);
   - symlink following differs per tool;
   - error codes are a mix of -1/-2/-5/-13 that are not errno, and the two filesystem servers return different
     codes for the same case.

   **Adopt real errno numbers now**, before more programs depend on "-1". It is cheap today and expensive later.

4. **Interrupts doing kernel work is the main structural issue.** It also blocks the planned display server: before
   moving the display out of the kernel, the input path needs to become "IRQ queues bytes, a process does the
   work". Do that first and the display-server move becomes much easier.

5. **The security story needs one honest paragraph.** The docs say users and permissions give "protection against
   honest mistakes". Today an honest `kill 2` takes the system down, and raw IPC bypasses every check without any
   memory poking. Batch D is small; after it, the documented promise is true.

6. **A syscall number registry.** Number 75 is already claimed twice (job control on main, floppy in the
   worktree). Put a "next free number" table in kernel.h or architecture.md section 7, and let each session claim
   numbers there first.

7. **Merge pressure.** drivers conflicts with main in the Makefile (UAPPS/RAMAPPS). Every branch grows the kernel,
   and the floppy has to fit kernel + RAM root, so the RAM/mount root sizes must be recalculated after every merge
   (zenixfs alone adds 27 KB of kernel). A merge-day order: main's staged work first, then drivers, then zenixfs,
   then floppy.

8. **Testing.**
   - `make test` checks nothing and always passes.
   - The serial scripts only know `sleep`, so everything rests on fixed waits.
   - users-test matches substrings that also appear in the echoed typing.
   - Many features marked "verified" have no checking test: /dev files, double-indirect files on ext2, the shell
     features, the terminal, RTC, less, man and date.

   Two small changes would help most: a `wait <regex>` command in `serial-tap.py`, and a `make check` that runs the
   strong tests with private serial and scratch paths and fails loudly. Also add an e2fsck run after cmds-test:
   it would have caught C1.

   **fixed** (76276d5; the e2fsck after cmds-test came with C1, 5c74081): `wait REGEX [timeout]` in serial-tap.py,
   used for the first prompt and the console logins of the strong tests; `make check` / `make test` run
   `tools/check.sh` (host tests, then the emulator tests one at a time with their own serial port and output
   directory, a table, non-zero on any failure; floppy-test named as not run). The "verified" without a checking
   test were corrected in features.md (22b06e3): RTC, scrollback, the escape codes, the function keys and the font
   are "read" now; double-indirect files are checked on the host. The batch D/E checks of users-test match whole
   lines (users-d-checks.sh); its older checks still match substrings.

9. **Memory budget for small Amigas.**
   - Every program carries about 14 KB of libz (4 KB output buffer, 2 KB environment) whether it uses it or not.
   - One `sh` costs about 135 KB plus its arena, and each `$(...)` spawns another.
   - On a 2 MB chip-only A1200 two levels of nesting is a big share of RAM.

   Splitting libz into an archive (or `-ffunction-sections --gc-sections`) and allocating the environment lazily
   saves 2-6 KB per process. Builtins inside `$(...)` without a new sh would save much more.

10. **Performance hot spots worth fixing before measuring:**
    - **Terminal output is capped at serial speed** (about 11.5 KB/s) because every byte is mirrored and
      `serial_putc` spins when the ring is full. Mirror only when a cable or test asks for it.
    - **`wake_io()` wakes every waiting process on every key or pipe chunk.** Per-object wait channels would fix
      it.
    - **Copies are byte-by-byte.** `memmove` and the pipe copy move one byte at a time, and `copy_str` checks
      `user_ok` per byte.
    - **ext2 writes about 5-6 blocks synchronously per data block**: zero-fill, data, bitmap, descriptor,
      superblock, inode.
    - **One IPC round trip per directory entry.** Return several entries per call.
    - **sh's `echo` makes one write per word** (one per character with `-e`).

11. **Docs.** Fix the contradictions in one pass:
    - command counts 20 / 77 / 84;
    - "about 55" system calls (really 72);
    - 13 matrix setups (really 14);
    - "ZenixFS planned/nothing built" in four files;
    - the multi-FS VFS "not done";
    - DESIGN milestone 2 "tested on a real A1200";
    - D5's "not from Linux GPL code" versus the GPL-2 decision;

    - commands.md pointing at `rootfs/usr/man`;
    - the "sh asks for 40 KB" stack size;
    - README "fast" against limits.md "no speed claims";
    - the guard words that do not exist.

    Then teach `docs-check.sh` to compare those counts with UAPPS, kernel.h and the matrix configs.

    **fixed** (22b06e3): every document read against the code and corrected (106

      paths" rule (the repo has no remote yet, so nothing is exposed).

    **fixed** (4feb04f: SPDX lines on every Zenix source file, MIT notices for regex.c/regex.h and miniz, the

## Part 4 - First real-hardware boot checklist (PiStorm A1200)

0. Use a spare SD card or an image of yours (`dd` on Linux). Connect the serial cable (115200 8N1): it is the only
   witness. Use native video, not the Pi's HDMI. Cold power-on. Ideally batch A is done first.
1. (Done in code, A8: the bootblock no longer writes 0x1000 while AmigaOS lives; no test needed.)
2. Boot `zenix-ram.adf` from the Gotek. A red screen means AllocMem/DoIO failed; a guru means stage0. The floppy LED should go off before the kernel's first message (A10).
   Without a serial cable: the screen colour names the step it stopped at, and after Ctrl-Amiga-Amiga the next boot
   shows the previous boot's last lines (A11/A12; the table and what to do are in pi-first-boot.md).
3. No serial banner at all: A2 (stale code at the jump), A7 (overlap) or A3 (on a 060).
4. Check the `cpu:` line (expect 68040 under Emu68), the `ram` lines, and `kernel at` (0x01040000 or above).
5. Check the `pi:` line: Emu68, BCM2711, emmc around 0xF2340000, mailbox around 0xF200B880.
6. Look at the line after `cache: instruction cache on`. Nonsense or a hang there is A1 (now `cpusha`).
7. Look at the screen: a blue bar and text. "no ROM font" means a font/home collision; a stripe means the sprites
   are not reset.
8. `ide: no drive found` should come at once. If the clock then freezes or everything crawls, it is the INT2
   storm (A9); `dmesg` would show `ide: stray Gayle IDE interrupt`.
9. The emmc stages: the first one that fails names the problem. Do not write to the card.
10. In the shell, run `ls`, then `cat /etc/motd`, then `ls` again. A program behaving like the previous one is A2.
11. Type fast (lost or doubled keys are A4), hold a key (repeat, A5), then try `å ä ö | $ @ ~ [ ] { }` (A5: `|` is
    Shift + the key left of Backspace, `[ ] { }` are Alt / Shift+Alt + å and the key right of it, `@` Shift+Alt+2,
    `$` Shift+4, `~` Alt + the key right of å). Check whether the floppy LED is still on (A10).
12. On any failure, note the last serial line and photograph the screen.
