Found while fixing (2026-10-26; fixed next, before block 2):
- **F1 serial-tap's `wait` can match the typed echo:** it searches all output since the last `send`, and the line
  editor redraws the prompt as each key is typed, so "wait for the prompt" after `send reboot` matches at once. Older
  update-test setups use that pattern and may pass by luck. Fix in the tap (match only output after the echoed line
  ends) and re-check every script that waits for a prompt after a send. **Fixed** (this commit: after a `send` whose
  text ends a line, a `wait` searches only from the first line feed that arrives after the tap typed the text's last
  `\r`/`\n`; a `send` without a line end keeps the old rule, and `waitecho` keeps it on purpose (cu-test, where cu
  owns the port and nothing echoes the PC's line). Every script checked: the waits for the prompt after `send reboot`
  (update-test install, zenixboot-test's bootmenu script, svc-test's svctab part), after `exit` (pure-test's shells)
  and after `termtest scroll` (colour-test) matched the echo at once and now wait for the real prompt; all other waits
  after a typed line look for markers the echo cannot hold. Test: new host test tools/tap-test.sh (in `check.sh
  host`): a fake shell that redraws its prompt with each key and runs each line for 2 s; with the old tap every line
  was typed before its prompt (fails), now none is; ZENIX_TAP_TRACE=FILE logs each wait's time: zenixboot-test
  bootmenu's wait for the prompt after `send reboot` and the new boot's klog line took 0.0 s with the old rule (the
  echo) and 1.9 s now (the new boot's prompt))
- **F2 a typed line of about 260 characters loses characters silently** (`break` arrived as `ak`). Find where (the
  serial input ring, the tty line buffer, or the shell's line editor) and either keep every character or refuse the line
  with a message (CLAUDE.md: a limit that is hit says so). **Fixed** (this commit; found: two silent limits. The
  cooked tty line held 255 characters and took no more without a sound on the serial port, so a line typed ahead
  while a command ran lost its middle, and the rest, typed after the shell's editor took over, ran; the line editor
  held 478 and ran the cut line. The serial ring (1 KB) is not the cause at the tap's 50 characters a second. Now the
  tty holds 511 (more than the editor, so a line typed ahead for the shell is never cut there); past a limit each
  key rings the bell (on the serial port too) and the whole line is refused at its end with a message, "tty: the
  line was too long (more than 511 characters): not taken" or "sh: the line was too long (more than 478 characters):
  not run" (status 2), never handed on cut; the tty's mark outlives the switch to raw mode, so no tail of the line
  runs; a recalled history line cut to 478 is refused the same way. Test: jobs-test, typed through the tap: a
  477-character line at the prompt and a 469-character line typed ahead arrive whole, a 1000-character line at the
  prompt gives the message and status 2 and runs nothing, a 718-character line typed ahead and cut by the switch to
  the editor and a 620-character one refused in cooked mode give the tty's message and run nothing, the next
  commands run; the old code fails 6 of these checks (the cut lines ran))
- **F3 zup's messages are lost when it is killed** (buffered output): its progress and error lines go out unbuffered
  or are flushed per line. **Checked: not buffered; test added** (this commit: zup's messages all go through `say`,
  libz's `printf`, which writes each call with one write() - only `oputs`/`oprintf` collect output - so nothing is
  kept back; libz's default is unchanged (right as it is: `printf` unbuffered, the buffered calls chosen by the
  programs that print much). Shown in the emulator: a slowzup build whose stage-2 zup printed two lines with
  `printf` and was then stopped by boot had both on the console; the stage-2 message now goes through `say` like
  every other (it was a bare write). Test: update-test slowzup checks that stage 1's progress line and stage 2's
  message are on the console before boot's "stopped after". Not done, being a new feature: copying zup's lines into
  the kernel log, so that `dmesg -p` after a power cut would show them; they are on console 1 only)

Found by the D16 design review (2026-10-26; fixed in the D16 build's first commit): **a stopped server runs** -
`proc_stop` readies a server sitting in receive, it becomes stopped inside `schedule`, but the port's `waiter` still names
it and `ipc_enqueue` readies it. Fix: `ready()` refuses `P_STOP`; `proc_cont`/`proc_kill` use a forcing variant.

Found while adding useradd (2026-10-26; fixed after F1-F3):
- **F4 sh acts interactive when its input is a pipe:** with no script and no `-c`, `shell_main` always sets
  `interactive = 1`, so `echo id | su anna` shows prompts and line-editor redraws in the output. bash is interactive
  only when its input is a terminal. Fix: read commands from a non-tty stdin like a script, but byte by byte from a pipe
  (as bash does), so a command that reads the rest of stdin (`printf 'echo a\ncat\nx\n' | sh`) gets it; no prompts,
  no history; compare with bash in cmds-test.
