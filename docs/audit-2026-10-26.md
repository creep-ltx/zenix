Found by the previous helper (2026-10-26, update-test `powercut`):
- **F5 a power cut during an update leaves the root damaged for e2fsck** (`powercut` failed "the root: e2fsck -fn
  clean" in about 2 of 3 runs, also on the old code; seen: inode 134, `/etc/motd`, "ref count 2, should be 1").
  **Fixed** (this commit). Cause, measured on the host (zup on the real ext2 server, `tools/host/zup-ext2.c`, the power
  cut after each of an update's 2212 block writes, then zup again): ext2 has no journal and most of zup's requests
  write several blocks - a hard link raises the count, then adds the entry (zup links some 300 files into prev-V/f/,
  so a cut there lands between the two about half the time); a file write allocates blocks, then writes the inode -
  so 1830 of the 2212 cuts left something e2fsck reports. Most are **leaks** (a count one too high, an unnamed inode,
  blocks or inodes marked in use that nothing holds, free counts off): zup's rollback and the reinstall never touch
  them (the extra count is on the old file, whose names zup keeps or removes as planned; the leaked blocks have no
  name at all). But some 40 cuts left **worse than leaks** on the old code: freeing a file (delete, `O_TRUNC`) cleared the
  bitmap bits before the inode let go of its blocks, so a cut left a file holding blocks marked free and the next
  file got them too (e2fsck: "Multiply-claimed blocks", a damaged directory block after the reinstall); `mkdir`
  added the entry before raising the parent's count (a count below its names); `rmdir` of a directory whose
  subdirectory a cut had left unnamed left that `..` naming a freed inode; and zup wrote its result line after
  marking the root clean (leaks on a root marked clean). Fix: `kernel/ext2.c` writes the inode without its blocks
  first and frees them after, the inode number last (`release`, `ext2_truncate`; the extended-attribute block the
  same way); `mkdir` raises the parent's count first (and gives the new directory back if the entry cannot be
  added); `rmdir` refuses (-ENOTEMPTY) a directory whose count says a subdirectory still points at it; zup writes the
  result line under the "needs a check" mark. Now every cut leaves at worst leaks, on a root marked "needs a check".
  The second failure ("the journal was cut short: nothing had been changed" not accepted) was the test being too
  strict: a cut while the journal itself is written leaves it without its `end` line, and nothing had changed then
  (the journal is written and synced before any change); the check accepts it now. Test: zup-host-test section 3 (in
  `check.sh host`): the 2212 cuts, then zup, then the bundle again: e2fsck finds at worst leaks (`tools/e2safe.py`
  sorts its findings), the root stays marked whenever it finds something, the new version at the end; on the old code
  76 checks fail, in some 40 cuts (multiply-claimed blocks, blocks in use marked free, counts below their names, leaks on a root marked
  clean). update-test `powercut` checks the root after the cut and after the next start: e2fsck clean, or at worst
  leaks with the root marked "needs a check" (run 6 times side by side: 6 of 6 passed; 2 left leaks, 3 were
  cut while the journal was written, so 5 of the 6 would have failed the old checks). The rename test of
  ext2-host-test still passes. **The repair, done next (DESIGN D17, docs/d17-ext2-clean-mark.md, two reviews; branch `fsck`):** boot
  checks an ext2 root that is not marked clean before anything writes to it: the root server first serves it
  read-only without taking the device (`-fsck`), boot runs `/bin/fsck.ext2 -y` on it, then starts the writable
  server; `mount -a` does the same for a marked volume of `/etc/fstab`. fsck.ext2 now repairs every leak a cut
  leaves in one run (a file size short of its last block as e2fsck does, orphans attached after the bitmaps are
  repaired and checked again by itself, empty unnamed files cleared) and marks the volume clean only after a run
  that writes nothing finds nothing. (The targeted repair by zup was not built: about 60 of the 1830 cuts.) Tests:
  zup-host-test section 3, each of the update's cuts that left something is repaired by one `fsck.ext2 -y` (e2fsck
  -fn clean, state clean; the old fsck.ext2 marks nothing clean, and before the size rule 1371 of the 1971 were not
  repaired);
  ext2-host-test, the same for a workload's cuts and a cut after each of fsck.ext2's own repair writes; the new
  emulator test rootcheck-test part r (leaks put in by debugfs are repaired at boot; all 7 checks fail on the old
  code) and update-test `powercut` (the second start checks the root, which is then e2fsck clean, not only leaks).
- **F6 an ext2 volume is never marked "needs a check" while it is mounted** (found with F5): Linux clears the clean
  bit at a writable mount and sets it at the unmount, so a crash at any time gets checked; Zenix's fsd marks the volume
  only after its own crash in a request (D11) and zup while it installs (D15). A power cut during ordinary use (a `cp`,
  an editor saving) leaves its leaks (F5) on a volume that says clean, and `e2fsck -p` on the PC would skip it.
  **Fixed** (DESIGN D17, docs/d17-ext2-clean-mark.md, two reviews; branch `fsck`), not as proposed: Linux's "not
  clean from mount to unmount" would mean a check after every switch-off (the root is never unmounted), so fsd
  follows AmigaOS FFS's bitmap rule: the volume is marked (written and flushed) before the first change after a
  clean moment and clean again one second after the last change, at `sync`, `reboot`, the reset warning and
  `FS_QUIT`; never while a deleted file is still open, while zup holds the mark, or when it needs a check (not clean
  at the mount, a crash in a request, a failed write, damage met). `FS_MARK` answers "needed no check" (fsd's own
  short mark does not count, so zup clears what it set) and its 0 never clears a real need. Tests: ext2-host-test

  `mount_search` (kernel/vfs.c) when the path crosses into a mount: for a caller other than root (uid 0 or a service's
  program, D11) it asks the parent's server `FS_LSTAT` of the mount point with the caller's ids, up through nested
  mounts to the root, and any error refuses the path. Measured in FS-UAE (200 stats through a floppy mount as a user):
  0.894 s before, 1.237 s uncached (1.7 ms, +38% a call), so a success is cached per mount for one uid and gid until
  any chmod, chown, rename, rmdir, unlink, mount, umount or server start: 0.905 s (no measurable cost; root's 0.886 s).
  Kernel +504 bytes. Test: `tools/mounttest.sh`: with `/tmp/al` (the user's, 700) and mounts at `/tmp/al/mnt` and
  `/tmp/al/mnt/sub`, guest cannot cat, ls or cd through either mount ("permission denied"; the old kernel let guest do
  all three), the owner and root can, and guest could before the chmod (the cached answer is dropped by it).
- **F14 a service load can wait for itself (found by D26's review, read from the code, not run):** while a server
  program is loaded (`svc.c` SV_LOADING), the loader's own `fs_exec_open` can reach the same held port; `svc_call`
  (svc.c 300-304) queues it and the loader waits for itself with no deadline (the start deadline `svc_born` is only
  set in SV_STARTING). Fix: `svc_call` refuses (-ECONNRESET) when the entry is SV_LOADING and its loader is the caller.
  Queued for the main line, with a test that reproduces it first.
- **F15 link targets over 255 bytes are cut silently (found by D26's review):** `ext2_readlink(..., 255)` (ext2.c 601)
  and zfsd's readlink cut a longer target from a volume written elsewhere, and a prefix can name another file. Fix:
  answer -ENAMETOOLONG instead of using a prefix. Queued for the main line, with a test image.
